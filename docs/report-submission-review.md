# Report submission, review, and merge workflow

This document describes the implemented portion of Issue #287. The feature uses POMAS's existing domain services and ledgers. Submissions are proposed snapshots, not a second farm accounting ledger.

## Operational roles

- **WORKER:** can create/save drafts, submit reports, view own submissions, checks, comments, decisions and merge references, and comment on own submissions. Cannot access farm-wide views, review queue, user administration, or direct ledger APIs.
- **ADMINISTRATOR:** retains the existing farm-owner operational workspace and manages user accounts/roles. Can submit and view own reports. Cannot inspect other users' submissions or use Manager review/decision/merge APIs.
- **MANAGER:** can use farm operations, view farm-wide submissions, assign reviewers, comment, request changes, reject, approve, authorize overrideable warnings, and merge. Cannot manage user accounts or roles.

The issue's capability matrix conflicts with its repeated detailed role rules and User Administration section. The implementation follows the detailed rule that Administrator is not a reviewer and cannot view other users' submissions. Reconcile the matrix before changing this boundary.

## Supported report types

The current form maps reports to existing POMAS domain services:

| Report type | Existing official service |
|---|---|
| Daily operations | Daily operations |
| Mortality / culling | Bird population events |
| Health observation | Health management |
| Drug treatment / vaccination | Health management |
| Egg collection / egg sale | Egg management |
| Weight record / bird sale | Broiler production |
| Feed usage | Feed management |
| Farm expense | Expense ledger |

Batch and feed references are loaded from the farm host. Report authors select active batch IDs and active feed type IDs rather than typing arbitrary references.

## Submission and versioning

- A report draft is stored locally on the author device and synchronized as a server-side DRAFT when the host is reachable.
- Saving a server draft does not submit it.
- Submission requires an explicit action and a live host connection. The renderer stores a submission-attempt key in the local recovery draft before sending the request.
- A required draft-creation Idempotency-Key is bound to a SHA-256 hash of report type, title, and payload. Reusing the same key with different content returns HTTP 409.
- The submit endpoint also requires an Idempotency-Key. It is persisted atomically with the SUBMITTED transition; retrying the same key returns the existing submission without appending another SUBMITTED event, audit entry, or notification. A different key cannot submit the same already-submitted version again. Saving a new editable version clears the previous submit key so that version can be submitted once.
- Every server save appends a new immutable version. The report type, title, and payload are all versioned.
- The author can edit DRAFT or CHANGES_REQUESTED reports only. Submitted, approved, rejected, and merged versions are not editable.
- Server receipt and audit timestamps are generated by the backend. Event date/time and any late reason are retained in the submitted version payload.

## Lifecycle

A new submission transitions from DRAFT to SUBMITTED and then, after checks, to one of:

- PENDING_REVIEW
- FLAGGED
- BLOCKED

A Manager may return a report as CHANGES_REQUESTED, reject it, or approve the exact submitted version. Approval does not update official farm records. A separate merge operation transitions APPROVED → MERGING → MERGED.

A later merge recheck can return an approved version to FLAGGED or BLOCKED. Decisions and check runs remain immutable; a new Manager decision can be recorded after the report returns to review.

## Automated checks

Checks run when a report is submitted and again immediately before merge.

Current checks include:
- **Permission gate:** every submit, review, override, assignment and merge action is guarded by the authenticated role. Review and merge actions are Manager-only; authors cannot review, authorize warnings on, or merge their own submissions. Automated check runs also record that the actor has an allowed role and the submission belongs to the active farm.
- **Version integrity gate:** every check run verifies that the report type, current version, submitted version and JSON payload match the exact immutable version being reviewed. A mismatched or missing version is blocked.
- DTO/Bean Validation for the report type.
- Required active batch reference and farm ownership.
- Batch type compatibility for egg and broiler reports.
- Event date not earlier than batch placement.
- Mortality, culling, and bird-sale quantity not exceeding known live population on the event date.
- Active farm feed type, applicable batch type, and unit validation for feed usage.
- Event date/time in the configured farm timezone, no future event time, and a reason plus Manager authorization for events older than 24 hours.
- Conservative duplicate-submission detection requires the same report type, batch, business date, and JSON-normalized immutable submitted payload. A shared house/batch and date alone never makes two events duplicates; distinct quantities, event times, reasons, notes, or other payload facts remain separate reviewable submissions. The lookup resolves each report type's date field (eventDate, recordDate, usageDate, or occurredDate).
- An official daily-record conflict check before a DAILY_OPERATIONS submission can be approved. It exposes the existing record ID and current notes because the daily operations adapter may update that day's existing record.
- Exact official expense duplicate detection using farm, batch scope, business date, category, amount, and normalized description. Similar but non-identical expenses remain a Manager judgement rather than an automatic rejection.
- **Stale-data gate:** the complete validation set is rerun immediately before merge against current farm, batch, feed, population and official-record data. A new duplicate/conflict or invalidated reference returns the approved submission to FLAGGED or BLOCKED instead of merging. The check run records `CURRENT_DATA_REVALIDATION` when this second validation pass has run.

Permission checks are enforced at the service boundary and cannot be bypassed by calling the API directly. Permission and version-integrity checks are also retained in the submission's check history. A stale-data recheck does not silently authorize newly discovered warnings; the Manager must inspect and authorize them against the current check result.

Outcomes:
- **PASSED:** no issue detected.
- **WARNING:** requires Manager inspection. Only checks marked overrideable can be authorized, and every override requires a separate reason recorded against the exact check and version.
- **BLOCKED:** cannot be approved or merged until corrected.

A missing late reason, invalid or missing batch, invalid payload, future event, impossible population quantity, or invalid feed reference blocks the report. Likely duplicates and late reports with a reason are warnings, not automatic rejections.

## Review Centre

Manager-only APIs provide:
- Farm-wide queue filtering by status and report type.
- Submission detail with author, versions, checks, comments, decisions, assignments, and activity history.
- Active Manager reviewer directory and assignment/reassignment.
- Comments, request changes, reject, approve, and warning override.
- Explicit merge of an approved version.

A Manager cannot approve, override warnings on, or merge their own submission. Assignment does not grant additional permissions.

## Atomic merge and provenance

The merge flow:
1. Revalidates the approved submitted version against current farm data.
2. Verifies current, submitted, and decision versions still match.
3. Atomically transitions the submission to MERGING using a unique idempotency key.
4. Calls the existing domain service for the report type.
5. Inserts a provenance link from submission/version to the created official record.
6. Appends merge history and audit events, then marks the submission MERGED.

All operations execute in one database transaction. A domain service failure rolls back official writes, provenance links, and the MERGED transition. A retry of an already-merged submission returns its existing result and does not call the domain service again. The Manager Review Centre derives a stable merge key from the submission ID and approved version, so a timeout or application restart retries the same merge operation rather than generating a new key.

## Remaining Issue #287 work

The first Review Centre hardening increment adds official-record conflict checks for existing daily records and exact duplicate expenses, plus regression coverage for a failed provenance write and competing version-checked review transitions. This is deliberately narrower than a universal duplicate rule.

The following are still not complete and must not be represented as complete:

- Report-type-specific official-record comparison for health, vaccination, drug, egg, weight, feed, mortality/culling, and sales records. Each needs its own business identity and conflict semantics; same-day activity alone must not be treated as a duplicate.
- Typed post-merge correction adapters beyond `WEIGHT_RECORD`. Weight corrections preserve the original official row, create a replacement through the existing production service, and link both records to the immutable source submission. Other transaction families remain blocked until their owning services can reverse and rebuild dependent ledgers atomically. Do not implement a generic table-name-based correction endpoint.
- Full concurrency coverage for competing merge attempts and concurrent writes to the same domain records.
- Failure-injection coverage for every report adapter and each write boundary, including audit, domain side effects, provenance, and merge completion.
- Network interruption/retry status reconciliation, packaged Electron, backup/restore, and full end-to-end acceptance coverage.

See [Review Centre hardening](review-centre-hardening.md) for the focused regression and manual test plan.

Emergency incidents are stored separately from farm ledgers. Reporting schedules and mortality thresholds are configurable but start unset; the application does not invent defaults. Missing reports are explicitly labelled missing, never interpreted as zero activity. Configured mortality thresholds can create Manager notifications and review warnings, but do not automatically change official records.

Evidence files are stored as validated SQLite BLOBs, associated with an immutable submission version. Supported formats are JPEG, PNG, PDF, and UTF-8 text, with a 5 MB per-file limit and 10 files per version. Because the bytes are stored in the same database, ordinary database backups include the evidence without a separate filesystem path.

## Phase 6: emergency alerts, schedules, missing reports, and notifications

The emergency and reporting workspace is available from **Alerts & Reporting** for all operational roles.

- Any authenticated Worker, Administrator, or Manager can submit an emergency incident. Workers and Administrators see their own incidents; Managers see the farm-wide queue.
- Managers can acknowledge incidents, escalate them with a required reason, and resolve them with required resolution notes. These actions append incident events and audit history. Escalation sends a renewed Manager notification.
- Emergency incidents remain separate from official records. A linked operational change must still be submitted as a normal report and follow the review/merge workflow.
- Managers can create daily or weekly reporting schedules by report type and farm, house, or batch scope, set local due times and grace periods, and pause/re-enable schedules. Schedules start unset; the application does not provide invented deadlines. Missing tracking begins no earlier than schedule creation or its most recent reactivation, so paused or pre-configuration periods are not reported as missed.
- Missing-report tracking evaluates only enabled schedules and displays overdue periods as **MISSING**. The explanatory copy explicitly distinguishes missing from zero activity. The tracker does not create daily records or other official ledger entries.
- The notification inbox is recipient-scoped. It includes emergency incidents, escalations, configured mortality threshold alerts, overdue schedules, report submissions requiring review, assignments, discussion updates, and review decisions. Users can mark their own notifications as read.
- Notification persistence remains local in the existing SQLite `manager_notifications` table. Repeated events refresh the matching notification and return it to unread state; no cloud push, email, or SMS service is introduced.

## Worker phone submission (Issue #316)

- Workers can create, save, and explicitly submit supported reports from the production same-origin browser workspace on a phone connected to the host PC's trusted private Wi-Fi.
- Use the existing My Reports form, draft recovery storage, `POST /submissions`, and `POST /submissions/{id}/submit` contracts. Do not add a mobile-only endpoint or bypass the submission workflow.
- The phone must reach the host over the LAN before a report can be submitted. Offline drafts remain local and recoverable; they are not submitted until the host is reachable.
- Keep the create and submit idempotency keys stable across retries. A lost response is an unknown outcome and must be reconciled against the server submission before local cleanup; never ask the Worker to create a second report to recover.
- The backend remains responsible for Worker identity, farm scope, payload validation, duplicate checks, late-report rules, and lifecycle transitions. A successful submission enters Manager Review and does not write an official farm ledger.
- On phone widths, make Save draft and Submit for review full-width, touch-sized actions. Preserve the same form semantics and explicit submit action.
- Verify the Worker can submit a valid report over the LAN, receives backend validation for invalid data, and sees the resulting submission status. Interrupt the response after the server commit and retry with the same operation key to confirm exactly one submission event and no duplicate.
